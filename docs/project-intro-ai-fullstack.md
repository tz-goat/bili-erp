# Bilibili 收藏资产管理系统 - 求职版项目介绍

> 说明：以下内容按项目的**最终目标态**整理，用于简历、作品集和岗位投递表达；表述重点放在产品设计、系统能力和工程方法，而不是当前未完成的里程碑状态。

## 1. 项目一句话定位

一个面向重度内容收藏用户的 **AI 辅助资产管理系统**。  
我把 Bilibili 原本偏内容消费的收藏页，重构成一个偏 **ToB/ERP 工作台** 的管理后台，让用户可以围绕“导入、整理、分析、决策”完成个人内容资产治理。

## 2. 项目介绍

### 2.1 简历版

独立设计并开发一个基于 ERP 方法论的视频收藏管理系统，围绕 Bilibili 收藏夹构建“来源数据只读 + 本地增强数据可持续维护”的双层数据模型。系统支持全量导入、工作区双栏整理、关键收藏夹画像、AI/规则混合归位建议、确认闭环与后续同步状态管理，目标是把分散的内容收藏沉淀为可检索、可分析、可决策的个人知识资产。项目采用前后端分层架构，后端以 Node.js + SQLite 承接导入与内部 API，前端规划为 React + Ant Design，强调从前端视角向 AI 全栈方向延伸的数据建模、系统设计与智能助手集成能力。

### 2.2 详细版

这个项目的出发点，不是做一个“更好看的视频收藏页”，而是把一个典型的 C 端内容消费场景，重新抽象成一个 **管理型系统**。

我把用户在 Bilibili 的收藏夹、收藏项、稍后再看等来源数据，当作需要治理的“外部业务事实”；再把标签、分类规则、备注、整理状态、归位建议、确认结果和同步状态，建模为系统自己的“本地增强数据”。这样做的核心价值是：

- 让系统摆脱对上游页面形态的依赖，形成稳定的内部视图模型
- 让整理动作和分析能力可以持续积累，而不是每次都被平台页面打断
- 让 AI 只负责“建议”和“理由生成”，而不是黑盒式直接替用户决策

从产品结构上，它不是传统门户首页，而是一个典型的 **工作区型后台**：

- 左侧是来源容器导航：关键收藏夹、普通收藏夹、稍后再看池
- 右侧是当前容器下的明细表格、轻量统计和待处理状态
- 用户可以对关键收藏夹补充半结构化说明，作为规则匹配和 AI 建议的语义基础
- 系统按需对单条收藏项生成 3 个候选目标收藏夹，并给出短理由和证据标签
- 所有建议都必须经过人工确认，随后再进入本地确认状态和后续同步链路

本质上，我在做的不是“视频工具”，而是一个带有 **Agent 式辅助决策能力** 的轻量 ERP：  
它把“导入 -> 整理 -> 分析”收成一条稳定流程，把 AI 放在可解释、可审计、可回退的位置上。

## 3. 项目亮点

### 亮点 1：把 C 端收藏场景重构成 ToB/ERP 式管理系统

- 不是围绕观看体验，而是围绕整理、筛选、确认、分析和决策设计信息架构
- 将“工作区”定义为主操作界面，“工作台”定义为后续概览分析入口，页面分工清晰
- 用双栏明细、状态字段、待处理计数和轻量统计承接典型后台系统交互

### 亮点 2：建立了清晰的数据边界，避免来源数据和本地语义混写

- 明确采用“来源数据只读，本地增强数据独立管理”的架构
- 同一视频跨收藏夹出现时，抽象为一条主记录 + 多条归属关系，而不是重复存储
- 通过软失效机制保留历史关系，兼顾快照一致性与后续同步对账

### 亮点 3：把 AI 放进可解释、可控的业务闭环，而不是做黑盒自动化

- 建议链路采用“规则优先，AI 辅助”的混合策略
- AI 负责补充候选理由、证据标签和辅助判断，不直接写入最终结果
- 所有建议都走“生成候选 -> 用户确认 -> 本地落库 -> 后续同步”的可审计流程
- 这种设计更符合企业场景对稳定性、责任边界和人工兜底的要求

### 亮点 4：从一开始就按全栈系统去设计，而不是先写页面再补后端

- 在原型阶段就拆出 adapters / application / domain / routes / http 的后端层次
- 先固化接口契约、领域术语、ADR 和迭代计划，再推进最薄实现
- 让前端消费的是稳定 View Model，而不是直接拼接上游 API 字段

### 亮点 5：对“外部不稳定接口”做了工程级兜底设计

- 针对 Bilibili 非官方接口的不稳定性，收口到单独 adapter 层
- 导入链路加入有限并发、分页合法性校验、最大页数保险丝和单收藏夹失败降级
- 通过“读取全走本地库，刷新才触发上游同步”的模式，降低 UI 对外部接口抖动的敏感性

### 亮点 6：具备明显的 Agent / 智能工作流演进空间

- 当前核心已经具备“上下文感知 + 单任务建议 + 人工确认 + 状态闭环”的 Agent 雏形
- 后续可以自然扩展为：批量待整理发现、偏好画像生成、规则学习、任务编排和多来源聚合
- 相比开放式聊天机器人，这种以业务对象和操作边界为中心的 Agent 更接近企业可落地形态

## 4. 专业技能

### 4.1 适合放在项目后的专业技能

- 前端工程化：React、Ant Design、后台型信息架构设计、复杂列表与工作区交互设计
- Node.js 全栈开发：Express、内部 API 设计、BFF / 聚合层思维、前后端分层
- 数据建模：SQLite、关系建模、主记录与归属关系拆分、同步状态建模、软删除 / 软失效设计
- AI 应用设计：规则优先 + AI 辅助的混合决策链路、可解释建议系统、人工确认闭环、Agent 式任务设计
- 系统设计：领域建模、接口契约设计、ADR 沉淀、模块边界拆分、外部系统适配层设计
- 工程质量：错误分层处理、有限并发控制、防御性编程、上游异常兜底、文档驱动开发

### 4.2 面向岗位标签的技能表达

#### Agent

- 能把 AI 能力嵌入真实业务流程，而不是停留在聊天式入口
- 理解“建议生成、证据输出、人工确认、状态回写”这类 Agent 工作流闭环
- 重视可解释性、责任边界和人机协同，而不是追求完全自动决策

#### ToB

- 具备后台系统的信息架构意识，能围绕状态、列表、筛选、流程和数据一致性设计产品
- 能把业务动作拆成稳定接口、状态机和可回放的数据结构
- 更关注效率、治理、审计和长期维护，而不是单纯视觉包装

#### ERP

- 熟悉“整理、分析、决策”导向的信息组织方式
- 擅长把混乱来源数据重构为主数据、关系表、状态表和工作区视图
- 理解系统价值来自流程闭环和数据可信度，而不只是功能堆叠

## 5. 适合投递时使用的项目标题

- AI 辅助内容资产管理系统
- 面向个人收藏治理的 ERP 式后台系统
- 基于规则 + AI 建议的收藏整理工作台
- 视频收藏管理与智能归位系统

## 6. 可直接放进简历的项目亮点摘要

### 版本 A：偏 AI 全栈

独立设计并开发 AI 辅助内容资产管理系统，围绕 Bilibili 收藏场景构建“来源数据只读 + 本地增强数据管理”的双层模型，支持全量导入、工作区整理、规则 + AI 混合归位建议、人工确认闭环与同步状态管理，体现了从前端工程到后端建模、再到智能决策链路设计的全栈能力。

### 版本 B：偏 ToB / ERP

将 C 端视频收藏场景重构为 ERP 式管理后台，围绕“导入 -> 整理 -> 分析”设计工作区双栏结构、状态驱动的明细表格与本地增强数据体系；通过接口契约、领域建模和内部 API 设计，把上游平台数据沉淀为可治理、可审计、可扩展的后台系统。

### 版本 C：偏系统设计

从零完成视频收藏管理系统的产品建模与技术方案设计，建立 adapter / application / domain 分层架构，定义来源快照、归属关系、建议分组、确认状态和同步状态等核心模型，并将 AI 能力限制在可解释建议环节，避免黑盒自动改写业务数据。

## 7. 面试时可以强调的转型价值

- 我不是只会做前端页面，而是开始从“页面实现”转向“业务建模 + 数据建模 + 系统编排 + AI 辅助决策”。
- 我关注的不是把 AI 接进来就结束，而是 AI 放在哪个环节最合理、怎样保证可解释和可回退。
- 我更适合做带业务结构的 AI 应用、Agent 工作流产品和中后台系统，而不是只做展示型前端。
