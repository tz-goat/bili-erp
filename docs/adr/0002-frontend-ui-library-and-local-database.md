# 前端组件库选用 Ant Design，本地数据库选用 SQLite

本 ADR 补记两个此前只写了「定为」、没留下理由的选型决定。React 与 Node.js 的选型属于个人既有技术栈，不在此记录。

## Ant Design

### 背景

产品设计原则明确要求「无聊化界面」——弱化缩略图、推荐流和沉浸式浏览心智，以文字、表格、状态和图表为主（见 PRD 3.1、3.2）。一期唯一的主操作界面是 `工作区`：左侧是 `稍后再看池 / 关键收藏夹 / 普通收藏夹` 三级容器导航，右侧是当前容器下的收藏项表格，附带分页、关键词筛选和状态标签。

也就是说，这个产品在形态上就是一个中后台 ERP 界面，不是内容消费页面。

### 决定

前端统一使用 Ant Design 作为组件库。

### 理由

- 核心交互几乎全部落在 AntD 的现成能力上：`Layout/Sider`、`Table`、`Form`、`Tag`、`Statistic`，无需自研表格与表单底座。
- 项目是单人、非全职投入，组件库真正省下的是自研的一致性风险，而不只是代码量。
- 高密度数据展示是既定偏好：纯文字列表 + 表格，不使用头像和封面图，这与 AntD 的中后台默认风格一致。
- 初始化流程后续要接入 Agent 自动补全结构化字段，需要一个成熟的表单能力承载「草拟 + 人工微调」。

### 被否决的替代方案

- **shadcn/ui + Radix + Tailwind**：更轻、更可控，但高密度表格需要自行接入 TanStack Table 并重写分组、分页、筛选，对当前需求开发成本明显更高。
- **MUI**：Material 的视觉气质与「弱刺激、无聊化后台」的目标冲突，定制成本也更高。
- **Arco Design / TDesign**：定位与 AntD 高度重合，没有明显优势，且团队既有熟悉度不如 AntD。

### 已知代价

AntD 6 是较新的大版本，周边生态（Pro Components、社区示例）可能滞后，检索到的多数答案仍停留在 v5，遇到问题需要自行排查。这是选择新版本换来的一致性代价，一期接受。

## SQLite

### 背景

一期是单用户、单账号、本地运行、单机场景，没有远端部署需求。数据必须保留在本地（含 SESSDATA 等凭据文件不外泄），页面展示只读本地库，只有手动触发「导入/刷新」时才允许请求 B 站接口。数据模型有明显的关系建模需求：视频主记录与容器归属关系拆分、唯一约束、软失效（`is_active`）以及导入过程的事务保护。

### 决定

本地数据库使用 SQLite，并直接基于 Node 内置的 `node:sqlite`（`DatabaseSync`）实现，不引入 ORM。

### 理由

- 单机单进程的读写场景与 SQLite 的能力边界完全吻合，引入服务端数据库只会增加部署和运维成本，收益为零。
- 使用 Node 内置模块意味着零第三方依赖，`getDatabase()` 在进程内复用一份连接，开启 WAL 与外键约束即可满足当前需求。
- 当前 schema 需要的能力——唯一约束、外键、软失效过滤、`withTransaction()` 的事务包装——SQLite 全部原生支持，且无需额外建模层。
- 数据留在本地这一硬约束，决定了数据库天然不适合放在远端。

### 被否决的替代方案

- **Postgres / MySQL**：面向多写并发、多人与远端部署。一期这些需求为 0，现在迁移是负收益；数据库访问已收口在 `apps/server/src/adapters/db` 一层，二期若真要做多账号或托管，迁移面可控。
- **LowDB / JSON 文件**：更简单，但缺少事务、索引和唯一约束，撑不住当前的「主记录 + 归属关系」建模。
- **DuckDB**：分析型（OLAP）能力更强，三期做「偏好画像 / 图表聚合」时可能比 SQLite 更顺手；但一期是点查、分页、关键词过滤为主的 OLTP 场景，收益不明显，且会额外引入一个存储引擎。
- **ORM（Prisma / Drizzle）**：能带来类型安全和真正的 migration 能力，代价是多一层依赖和心智模型。一期手写 SQL 是合理的最小实现。

### 已知代价与后续触发条件

1. **单写者模型**：SQLite 同一时刻只允许一个写事务，并发写会串行或报锁。当前单用户无影响；一旦二期加入「定时全量同步」且前端同时在读，需要显式配置 `busy_timeout` 兜底。
2. **同步 API 阻塞事件循环**：`DatabaseSync` 是同步调用，导入数据量显著增大后需要考虑放入 worker，或替换为异步封装（如 `better-sqlite3`）。
3. **缺少真正的 migration runner**：目前由 `ensureMissingColumns()` 通过「缺哪列就加哪列」兜底新增可空列，只能覆盖加列，改类型或删列仍需真正的迁移工具。这是在引入 migration runner 之前的有意临时实现。
