# 归位匹配以本地既有信号为主，Agent 只做离线词表扩写

## 背景

归位匹配（一条收藏项 → 更适合放进哪个关键收藏夹）是本项目的核心判断。当前实现落在 [`suggestion-policy.js`](../../apps/server/src/domain/suggestion-policy.js)：只读取 `source_items.title` 与 `intro`，打分口径是「命中词表中的词数」。词表来自用户手写的 `folder_profiles.include_topics` 与 `keywords_json`。

这个实现同时承受三个压力：

1. **词表贫瘠且靠人工穷举。** `purpose`（用户写的自然语言说明）[不参与匹配](../../docs/suggestion-matching-logic.md)，用户必须额外把意图翻译成关键词。标题写成「Vue3 源码逐行拆解」时，词表里没有「前端」二字就永远召回不到。
2. **更多语义信号要付代价。** 首次收藏夹接口（`fav/resource/list`）拿不到分区与 tag，需要二次请求，[而项目已定 412/429 必须立即中止整轮](../../docs/progress.md)。数据越补越多，风控风险与耗时同步上升。
3. **想引入 Agent，但成本与可解释性存疑。** 逐条调用是 O(视频数) 的 token 成本，且会让 `evidenceTags` 的证据链断裂、结果不可复现。

同时有一个此前被忽略的事实：**首次请求给的信息远多于匹配器用到的**。

| `source_items` 已有列 | 来源 | 当前匹配器是否使用 |
| --- | --- | --- |
| `title` / `intro` | 首次请求 | 是 |
| `duration_seconds` | 首次请求，[已落库](../../apps/server/src/application/import-all.js) | 否 |
| `upper_name` / `upper_mid` | 首次请求，已落库 | 否 |
| `publish_time` | 首次请求，已落库 | 否 |
| `cover_url` | 首次请求，已落库 | 否 |
| `raw_json` | 首次请求，整个 media 原文已落库 | 否 |

即"要更准就得采更多数据"这个直觉，在已经付过成本的这一层上并不成立。

## 决定

1. **判定链路永远是本地纯计算。** 分类器只读本地库、只做确定性计算，绝不发起请求、绝不调用模型。库里有什么信号就用什么。
2. **采集与判定彻底解耦。** 「补齐数据」是一个独立的、可中断可续跑的后台任务，不是判定链路的前置条件。数据是否齐备只影响结果质量，不影响功能可用性。
3. **Agent 不进入判定链路。** 它只用于**离线、按收藏夹**扩写词表，产出经人工审核后落库，判定仍由规则执行。
4. **信号按"零成本优先"分三层启用**，且无文本证据的信号只影响排序、不影响召回。
5. **权重必须从数据算出，不拍脑袋。** 新增信号的强度口径要能追溯到统计结果，而不是人工设定。

## 理由

### 为什么判定必须留在本地

- 保住现有全部优点：可复现、可离线全量重算、零成本、[纯函数可单测](../../apps/server/src/application/suggest-item-target.test.js)。
- 规则可以在数秒内跑完全库，这类「覆盖率扫描」能力只有确定性计算才有。
- 一旦让判定依赖外部调用，`rank` 从"可信"退化为"仅供参考"，而落库表上还有 `UNIQUE (suggestion_group_id, rank)` 约束依赖它的确定性。

### 为什么 Agent 放在"扩写词表"而不是"逐条判定"

| | 逐条判定 | 扩写词表 |
| --- | --- | --- |
| 成本量级 | O(视频数) | **O(收藏夹数)**，与视频量无关 |
| 可复现 | 否 | 是（判定仍是规则） |
| 证据链 | 断裂（理由是生成的） | 保留（`evidenceTags` 仍是词） |
| 收益可度量 | 需人工标注集 | **可直接回测**（待整理夹召回数从 0 变 N） |
| 人工审核点 | 每条结果 | 每个收藏夹一次 |

它同时解决了背景里的第 1 条压力：用户只需写 `purpose`，结构化词表由 Agent 草拟、人工审核落库——这与项目既有的「Agent 自动草拟 + 人工审核微调」模式一致。

### 为什么关键收藏夹的存量成员是最高质量的词表语料

用户的 `include_topics` 是**声明式**的（他以为自己想要什么），关键收藏夹里已有的视频标题是**实例式**的（他实际收进去了什么），两者经常不一致。

因此同一个槽位有两种互补的实现：统计版从存量标题里挖高频词（零成本、只能挖到出现过的词），Agent 版从 `purpose` 语义扩写出没出现过的同义词。**统计版的产出正好是 Agent 版最好的输入**，两者不是二选一。

从 `source_folder_items` 读存量时必须过滤 `is_active = 1`（既有软失效约束）。

### 为什么无文本证据的信号不能参与召回

UP 主与共现信号都没有可展示的文本依据。若让它们参与召回，用户会看到「标题里一个字都没提却被推荐了」，可解释性当场断裂；而从"多路加权"滑向"隐式模型"只有一步之遥，这是项目此前明确排斥的方向。它们只应影响同分候选的先后。

同理，权重不拍脑袋：

```text
词 w 对夹 A 的权重 = (w 在 A 成员标题中的出现率) / (w 在全部视频标题中的出现率)
UP 主 u 对夹 A 的权重 = count(u 在 A) / count(u 在所有关键夹)     ← 用分布纯度，不用绝对数量
```

一个 UP 主在 A 有 7 条、在 B 有 5 条时，它是模糊的，不该给高权重。

## 被否决的替代方案

- **判定链路直接调 Agent（一条视频一次调用）。** token 成本随视频量线性增长；且项目下一步是「整理整夹（批量扫描）」，延迟会直接叠加成不可接受量级。
- **先补齐 L1 详情（分区/tag）再做匹配。** 把付费数据变成前置阻塞，与"零成本优先"相悖；且 L1 的收益未必高过免费的跨夹共现信号。
- **让 Agent 联网判断 UP 主 / 视频内容。** 引入延迟不可控、结果不可复现、外部依赖，且是 token + 请求双重成本。**注意：Agent 与规则拿到的输入是同一份（title + intro），换 Agent 并不会让系统"看懂视频"**——除非另行采集字幕或画面。
- **用 UP 主名字做语义匹配。** 名字对语义判断是噪音，离线模型无法处理长尾；但 `upper_mid` 作为结构锚点是有效信号，两者应分开处理。
- **把"视频已被归到另一个收藏夹"当作正向召回证据。** 它已经在那个夹里了，再建议一次没有意义。它的正确用法是负向过滤（候选剔除已在的夹）、共现传播（用它判断它的**邻居**）、以及识别"该视频的正确动作是移除而非归位"。
- **多路信号加权求和成单一分数。** 权重没有依据时，「可解释」会退化成「看起来可解释」。改为分层：文本命中负责召回，结构信号负责过滤与排序加成，各通道单独可解释。

## 落地顺序

| 顺序 | 内容 | 请求成本 | token 成本 | 收益可度量 |
| --- | --- | --- | --- | --- |
| 0 | 候选剔除"视频已在的收藏夹"；接入免费字段（`duration` / 跨夹分布） | 0 | 0 | 是（纯修正） |
| 1 | Agent 离线扩写关键收藏夹词表（以统计挖词为输入） | 0 | O(收藏夹数) | 是（回测召回数） |
| 2 | 用关键夹存量算词权重，替换等权打分 | 0 | 0 | 是 |
| 3 | UP 主 / 共现传播作为同分排序加成 | 0 | 0 | 需评估验证 |
| 4 | L1 详情补齐（分区 / 完整简介），后台任务、按需触发 | 唯一视频数 × 1 | 0 | 是 |
| 5 | 上线 2.5，开始积累 `item_decisions` | 0 | 0 | — |
| 6 | 用积累的 `item_decisions` 作为评估集，才谈得上证明"更准" | 0 | 0 | — |

第 1 步排在第 2-3 步之前：它的收益能用确定性的规则直接量出来，而信号融合在没有标注数据时只能靠个案感觉。

**审计先于实施：** 第 0 步之前先看一眼 `SELECT raw_json FROM source_items LIMIT 5`。凡是原文里已有、只是没提成列的字段，都属于零请求回填。

## 已知代价与后续触发条件

1. **冷启动无解。** 关键收藏夹内没有存量视频、说明也未填时，统计挖词与 Agent 扩写都没有输入，只能等用户先积累或先填写。
2. **召回上限受标题信息量限制。** 标题写成「【合集】第三期」时，规则与 Agent 都无从判断。突破这个天花板需要 L1 甚至 L2（字幕/画面），属于数据采集问题，不是匹配器问题。
3. **在积累评估集之前无法证明"变准"。** `item_decisions` 表目前只有读路径（`LEFT JOIN`），写入口是尚未开始的 2.5，因此表是空的。**它既不能作为特征源，也不能作为评估集**——在此之前新增信号只能靠代理指标（如待整理夹的召回覆盖率）判断，不能用它宣称准确率提升。
4. **L1 补齐需要新的任务 scope。** 应复用 `import_runs` 的任务记录形态与既有风控中止规则；断点续跑不需要进度游标表，待补队列直接由 `WHERE <新列> IS NULL` 从数据自身派生。
5. **扩写结果必须与用户录入分列存储。** 若直接写回 `keywords_json`，将无法区分词的来源、也无法单独撤销 Agent 的产出，违反「外部来源与本地增强分开管理」的既有边界。
6. **扩写会把成本转移到审核侧。** Agent 一次生成数十个词时，用户审核负担可能超过自己写几个词。缓解手段是用待整理夹回测生成结果，只展示能带来新召回的词。
