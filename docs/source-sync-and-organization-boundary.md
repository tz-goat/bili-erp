# 来源同步与整理边界

最后更新：2026-11-10

> 本文件只定义**来源同步（读）与整理范围**的边界口径。
> 写回与双向同步的落地设计见 [two-way-sync-design.md](file:///Users/dateng/pl-dashboard-2610/docs/two-way-sync-design.md)。

## 1. 这份文档要纠正什么

这次不是继续把导入体系做得更重，而是先把问题重新说清楚。

当前讨论已经被带偏到了两条不必要的方向：

1. 把 `导入` 和 `整理建议` 混成一条链路
2. 把 `所有视频` 都默认视为 Agent 需要治理的对象

这都不符合当前项目真正想解决的问题。

这份文档的目标是重新收窄主线：

> `导入/更新` 负责把来源数据拉进本地；
> `整理/建议` 只服务于少数需要整理的收藏夹；
> `Agent` 不是全库分类器，而是“待整理收藏夹 -> 关键收藏夹”的辅助判断器。

## 2. 当前系统实际上在做什么

根据现有实现 [`startImport()`](file:///Users/dateng/pl-dashboard-2610/apps/server/src/application/import-all.js#L24-L75) 和 schema 设计 [`schema.js`](file:///Users/dateng/pl-dashboard-2610/apps/server/src/adapters/db/schema.js#L1-L193)，当前导入逻辑本质上还是一条 `全量快照链路`：

1. 拉账号下全部收藏夹目录
2. 逐个拉每个收藏夹的内容
3. upsert `source_folders`
4. upsert `source_items`
5. upsert `source_folder_items`
6. 导入结束后，对本轮未再看到的归属关系做软失效

这条链路的特点是：

- 它是来源数据同步，不是整理动作
- 它以“平台快照”作为可信基线
- 它当前只有“全量导入”这一种主要入口
- 它的存储口径里，同一视频跨收藏夹会被合并为一条 `source_items` 主记录，再通过归属关系表区分来自哪些收藏夹

这套设计对“本地保存来源快照”是成立的，但它并不自动推出“业务上所有视频都该被当成同一个待整理对象”。

## 3. 当前讨论为什么会偏掉

偏差主要出在把两个层次混在了一起：

### 3.1 存储层的去重，不等于整理层的工作单元

现在的 schema 用 `source_items + source_folder_items`，是为了表达：

- 同一个视频在平台上可能出现在多个收藏夹里
- 本地没必要把视频主信息重复存很多份

这是一个 `存储与建模` 决策。

但它不应该被直接抬升成 `整理语义`：

- 业务上，用户关心的不是“这个视频在全系统是否唯一”
- 而是“这个视频出现在某个待整理收藏夹里时，是否适合归到某个关键收藏夹”

所以整理动作更接近处理：

> `某个来源收藏夹中的某条视频归属`

而不是处理：

> `整个系统唯一的一条视频实体`

### 3.2 不是所有收藏夹都要进入整理闭环

当前项目的核心不是“把账号里所有视频都自动分类完”。

更贴近真实需求的主线其实是：

1. 用户先选出少数 `关键收藏夹`
2. 这些关键收藏夹代表长期稳定的分类目标
3. 再从少数 `待整理的大收藏夹` 中挑出视频，判断哪些适合进入这些关键收藏夹

典型例子就是：

- `默认收藏夹`、`临时收集夹`、`混杂大夹` 是待整理来源
- `前端`、`产品`、`设计参考`、`职业发展` 这类才是关键收藏夹

所以 Agent 的职责不是扫全库，而是帮助用户从“混杂来源”里往“关键目标”里做筛选和建议。

## 4. 重新定义后的系统主线

建议把系统拆成三条清晰主线，而不是继续围绕“全量导入任务系统”扩展。

### 4.1 主线 A：来源同步

职责只有一个：

> 把平台上的收藏夹和收藏项拉到本地，形成可读取的来源快照。

它回答的是：

- 现在有哪些收藏夹
- 每个收藏夹里现在有哪些视频
- 本地看到的是不是最近一次成功拉下来的快照

它不回答：

- 这个视频该归哪类
- 哪些视频需要被整理
- 是否应该立即生成建议

### 4.2 主线 B：关键收藏夹建模

职责是定义整理目标，而不是扫描全库。

它回答的是：

- 哪些收藏夹是关键收藏夹
- 每个关键收藏夹主要承载什么内容
- 它们之间的大致边界是什么

这里的关键点是：

- `关键收藏夹` 是目标体系
- 不是所有收藏夹都值得写 profile
- 只有进入目标体系的收藏夹，才值得让 Agent 学习其语义

### 4.3 主线 C：待整理收藏夹的归位建议

职责是面向少数待整理来源，按需生成建议。

它回答的是：

- 当前这个大收藏夹里，哪些视频适合归到关键收藏夹
- 候选目标收藏夹有哪些
- 每个候选的理由是什么

它不应该变成：

- 每次导入后自动给全库所有视频跑一遍分类
- 给本来就已经归位明确的视频重复生成建议
- 把所有收藏夹都视作待整理池

## 5. 纠偏后的核心判断

### 5.1 “同个视频跨收藏夹是否视作一个”不该成为当前架构的主导问题

你的判断是对的：`现在不需要把它作为核心业务前提`。

更准确地说：

- 底层存储是否做视频主记录复用，可以继续是实现细节
- 但上层整理流程不该默认“同一视频只会有一个整理状态”

因为同一个视频可能同时出现在：

- 一个关键收藏夹里，表示它已经有明确归属
- 一个默认收藏夹里，表示它仍然是待整理来源中的候选

这两个语义不能简单折叠成一个全局唯一的“已整理 / 未整理”状态。

### 5.2 Agent 的处理范围必须收窄

Agent 现在应该只面对两类输入：

1. `关键收藏夹画像`
2. `某个待整理收藏夹中的视频集合`

然后输出：

- 哪些视频值得推荐归到关键收藏夹
- 每条视频的 1~3 个候选目标
- 理由与命中依据

不应该让 Agent 默认面对：

- 全账号所有收藏夹
- 全账号所有视频
- 所有视频都必须给出一个归类结论

### 5.3 “待整理”应该是显式范围，不是系统默认全集

后续真正需要建模的不是“全库待整理”，而更像是：

- 哪些收藏夹是 `关键收藏夹`
- 哪些收藏夹是 `待整理来源`
- 哪些收藏夹只是普通参考夹，不参与本轮整理

这样系统才符合真实使用习惯，也能避免 Agent 成本和界面复杂度失控。

## 6. 对导入架构的直接影响

在这个纠偏后的口径下，导入体系仍然要重构，但目标应该更克制。

### 6.1 导入重构的真实目标

导入侧现在真正需要解决的是：

1. 初始化时能拿到一份完整来源快照
2. 日常可以刷新单个收藏夹，而不是每次都全量重跑
3. 前端能知道最近一次刷新是否成功，避免“空夹”和“刷新失败”混淆

也就是说，导入重构首先服务的是：

- `来源可信`
- `日常刷新方便`
- `失败语义可解释`

而不是优先服务：

- 一个很重的导入中心产品
- 全量任务编排系统
- 复杂的全局任务历史分析

### 6.2 当前最值得保留的能力

现有全量导入仍然有价值：

- 它适合作为初始化入口
- 它适合作为低频对账手段
- 它能在需要时重建一份完整来源快照

所以它不该被否定，而应该被重新定位为：

> `低频基线导入`

### 6.3 当前最值得新增的能力

比“导入中心”更优先的，其实是：

1. 单个收藏夹刷新
2. 刷新结果可见
3. 当前收藏夹刷新失败时，工作区能解释“你现在看到的是旧快照”

这比先做一个大而全的导入任务系统更贴近眼前问题。

## 7. 对数据模型的重新表述

来源同步侧的建模口径在这里纠正；写回相关的表结构结论（新增 `sync_intents` / `sync_attempts`、废弃 `item_sync_status`）见 [two-way-sync-design.md](file:///Users/dateng/pl-dashboard-2610/docs/two-way-sync-design.md) 第 11 节。

### 7.1 来源数据层

来源数据层仍然可以保留：

- `source_folders`
- `source_items`
- `source_folder_items`

因为它解决的是“如何在本地表达平台快照”。

### 7.2 整理语义层

整理层不应该直接建立在“全库唯一视频待办”上，而应该围绕以下概念展开：

- `key_folders`：关键收藏夹，表示目标分类体系
- `folder_profiles`：关键收藏夹说明，表示目标语义
- `source folders to organize`：待整理来源收藏夹，表示建议输入范围
- `suggestions/decisions`：仅针对某个来源范围按需生成

这意味着后续如果要调整建议表结构，更合理的主语义可能是：

- `某来源收藏夹中的某视频候选`
- 或 `某次整理上下文中的某视频候选`

而不是简单地把 `item_id` 当成全局唯一待办主键。

## 8. 推荐的产品口径

### 8.1 初始化阶段

初始化仍然可以保持现在的顺序：

1. 先全量导入来源数据
2. 用户勾选关键收藏夹
3. 用户填写关键收藏夹用途说明
4. 进入工作区

这里不需要新增“导入中心”才能成立。

### 8.2 日常使用阶段

日常流程更应该是：

1. 用户进入某个待整理收藏夹
2. 如有需要，刷新当前收藏夹
3. 基于该收藏夹内容按需生成归位建议
4. Agent 只拿关键收藏夹画像作为目标集合来判断

### 8.3 导入相关 UI

导入 UI 先以轻量形态存在即可：

- 工作区里的“刷新当前收藏夹”
- 最近一次刷新状态
- 一个简单的导入历史页或抽屉

是否需要单独的“导入中心”页面，可以后置判断，不必现在就预设成核心页面。

## 9. 渐进式落地顺序

### Phase 1：先把问题边界修正

1. 文档口径从“全库任务系统”改回“来源同步 + 局部整理”
2. 明确 Agent 不做全量自动分类
3. 明确关键收藏夹与待整理收藏夹是两类不同对象

### Phase 2：补单夹刷新

1. 保留全量导入作为初始化与低频对账入口
2. 新增单收藏夹刷新
3. 给工作区补刷新状态提示

### Phase 3：重写建议链路口径

1. 把建议生成范围限定到指定来源收藏夹
2. 只把关键收藏夹作为候选目标集合
3. 避免把 `all items` 作为默认输入

### Phase 4：再决定是否需要导入中心

等单夹刷新、失败解释、历史记录这些最小能力稳定后，再判断是否真的需要独立页面承载导入任务管理。

## 10. 一句话结论

> 现在最需要的不是把导入体系升级成一个重任务系统，
> 而是先把系统主线收回来：
> 导入负责来源快照，关键收藏夹负责定义目标，Agent 只服务于待整理收藏夹到关键收藏夹的归位判断。
